# Data Model

Single source of truth for the schemas the Shared Data API owns. The Shared Data API is the only service that reads or writes either database (see ADR-005).

- **MongoDB** holds identity and policy reference data: `users` and `policies` (with embedded `vehicles`).
- **PostgreSQL** holds transactional claim data: `claims` and `claim_status_history`.

---

## MongoDB collections

### `users`

| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | Mongo-generated |
| `username` | string | Unique; used at login |
| `password_hash` | string | `bcrypt` hash |
| `role` | string | `customer` or `agent` |
| `display_name` | string | Shown in UIs |
| `created_at` | date | ISO 8601 |

Admin accounts do not live in `users`. The dashboard's admin credentials are env-supplied (see ADR-006).

### `policies`

| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | Mongo-generated |
| `policy_number` | string | Unique business key |
| `customer_id` | string | References `users._id` (role=customer) |
| `effective_date` | date | Policy start |
| `expiration_date` | date | Policy end |
| `coverage_type` | string | e.g. `auto-comprehensive`, `auto-liability` |
| `premium_cents` | int | Avoid floats |
| `vehicles` | array | Embedded list of vehicle subdocuments (see below) |

Embedded `vehicles` subdocument:

| Field | Type | Notes |
|---|---|---|
| `vin` | string | Unique within the policy |
| `make` | string | |
| `model` | string | |
| `year` | int | |

Vehicles are embedded (not a top-level collection) because they are always read with their parent policy and never modified independently in this project.

## PostgreSQL tables

### `claims`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | Generated by SDA on create |
| `policy_number` | text NOT NULL | References Mongo `policies.policy_number`; not a FK |
| `customer_id` | text NOT NULL | References Mongo `users._id` (role=customer) |
| `vin` | text NOT NULL | Snapshot of vehicle VIN at time of FNOL |
| `vehicle_snapshot` | jsonb NOT NULL | Snapshot of `{make, model, year}` from policy at claim time |
| `incident_at` | timestamptz NOT NULL | When the accident occurred |
| `description` | text | Free-text from FNOL submission |
| `current_status` | text NOT NULL | Latest value from the status enum |
| `assigned_adjuster_id` | text | References Mongo `users._id` (role=agent); set by SDA on triage |
| `created_at` | timestamptz NOT NULL | When FNOL submitted the claim |

The vehicle snapshot is stored on the claim because policies (and embedded vehicles) live in Mongo and can change independently. The snapshot preserves what was true at the time the claim was filed.

### `claim_status_history`

| Column | Type | Notes |
|---|---|---|
| `id` | bigserial PK | |
| `claim_id` | uuid NOT NULL | FK → `claims.id` |
| `from_status` | text | Null on the initial `submitted` row |
| `to_status` | text NOT NULL | New status |
| `actor_id` | text NOT NULL | References Mongo `users._id`; the assigned adjuster for simulator-driven transitions |
| `changed_at` | timestamptz NOT NULL | When the transition happened |
| `note` | text | Optional context |

Every status change writes a row. The latest `to_status` is denormalized onto `claims.current_status` for fast reads.

---

## Status enum

`submitted → triaged → investigating → settled → closed`

Plus a terminal `denied` branch reachable from `triaged` or `investigating`.

The background simulator (ADR-007) advances statuses on a tick; FNOL writes only the initial `submitted` row.

---

## Seed counts

The Shared Data API seeds these on startup if either DB is empty (idempotent):

| Entity | Count | Notes |
|---|---|---|
| `users` (role=customer) | 10 | 5 used as demo logins in `.env.example` |
| `users` (role=agent) | 5 | All 5 used as demo logins in `.env.example` |
| `policies` | 15 | Each with 1–2 embedded vehicles |
| `claims` | ~10 | Distributed across statuses for realistic dashboard input |

Admin (dashboard) is env-supplied (`DASHBOARD_ADMIN_USERNAME` / `DASHBOARD_ADMIN_PASSWORD`) and is not part of the seed.

---

## Write authority

| Writer | What it writes |
|---|---|
| FNOL (via Shared Data API) | New `claims` rows + initial `claim_status_history` row (`submitted`) |
| Background simulator (inside Shared Data API) | All subsequent `claim_status_history` rows; updates `claims.current_status` and `claims.assigned_adjuster_id` |
| Shared Data API seed routine | Idempotent inserts into `users`, `policies` on empty DB |

Customer Portal and Agent Portal never write to either database. They only consume read endpoints on the Shared Data API (see ADR-005).

## Schema enforcement

### MongoDB indexes

Applied at startup by `ensure_indexes()` (idempotent — `create_index` is a no-op if the index already exists).

| Collection | Field(s) | Type | Name |
|---|---|---|---|
| `users` | `username` | unique | `users_username_unique` |
| `policies` | `policy_number` | unique | `policies_policy_number_unique` |
| `policies` | `customer_id` | non-unique | `policies_customer_id` |

### PostgreSQL CHECK constraints

Applied at table creation. The status enum is the same one used by the simulator (ADR-007); a runtime import-time guard cross-checks the two in `simulator.claim_status._validate_status_coverage()` so they cannot drift.

| Table | Column(s) | Constraint name |
|---|---|---|
| `claims` | `current_status` | `claims_current_status_enum` |
| `claim_status_history` | `to_status` | `claim_status_history_to_status_enum` |
| `claim_status_history` | `from_status` | `claim_status_history_from_status_enum` (`NULL` allowed) |

### Schema evolution

Postgres schema is managed by **Alembic** (`apps/shared-data-api/alembic/`). The lifespan
runs `alembic upgrade head` on every start via `postgres.run_migrations()`. The current
baseline is `a51e64afbd0f_phase_3_baseline.py`. See ADR-008.

**To add a migration:**

```bash
cd apps/shared-data-api
# 1. Edit the model in src/shared_data_api/db/models.py

# 2. Make sure Postgres is running and your env vars point at it
docker compose up -d postgres

# 3. Autogenerate the migration (env vars: SHARED_DATA_API_POSTGRES_URL etc.)
uv run alembic revision --autogenerate -m "<short description>"

# 4. Inspect alembic/versions/<slug>_<description>.py — autogen does NOT detect
#    CHECK constraint edits, enum changes inside strings, or some index renames.
#    Hand-fix anything missed; commit the file.

# 5. Restart the SDA container — alembic upgrade head runs automatically
docker compose up -d shared-data-api
```

**Tests bypass Alembic** for speed: the autouse `_bypass_run_migrations` fixture in
`tests/conftest.py` routes `postgres.run_migrations()` → `postgres.create_all()` so
the SQLite-in-memory test fixture creates tables directly from `Base.metadata`. Tests
that need the real `run_migrations()` opt out with `@pytest.mark.no_run_migrations_mock`
(see `tests/test_run_migrations.py`).

**Downgrades** are supported (`alembic downgrade -1` or `alembic downgrade base`) but
are not part of the standard runbook — forward-only migrations are the expectation.
